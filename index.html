Strong, two-way schemas from the infrastructure to the database to the AI

01 · Alchemy

Infrastructure is just TypeScript

  • A resource is a value. Binding it to a Worker is what creates it.
  • InferEnv turns the bindings into the app's env type
  • alchemy plan shows the diff before anything changes
  • Stages (dev, demo, prod) are separate copies, each with its own settings
  • alchemy dev emulates D1, R2 and email locally
Alchemy v2 is built on Effect: the stack is an Effect program, and resources are yielded. Step through the highlights: resources, the Website and its bindings, the inferred type, and the stack. The state (what Alchemy has made) lives in your Cloudflare account, so anyone with access can deploy the next change.

01 · Effect

A service: the contract, not the vendor

The search code never sees env.AI or Vectorize. It asks for an Embedder and a VectorIndex, and the type says so. Forget to provide one and it doesn't compile. Tests provide in-memory versions.
01 · Effect Schema

One definition: the type, the rules, the messages

The messages are written for a person and, as we'll see, for a model. "Keep the title under 140 characters" is something both can act on.
01 · The core idea

Bidirectional schemas

Each boundary has one definition, and both sides are derived from it

Infrastructure alchemy.run.ts declares DB, AI, VECTORS
⇄
App code InferEnv types platform.env; Worker classes type their bindings
Drizzle tables TypeScript columns, constraints, indexes
⇄
Database SQL migrations out; typed rows back from every query
Effect Schema JSON Schema out, for tools and structured output
⇄
The model Its JSON decoded strictly: a typed value, or a list of fixes
Effect Schema Standard Schema out, for forms
⇄
People Field-by-field issues back, with the same rules on the server
This is the slide to remember. Each arrow both ways is generated, not hand-kept. When one side changes, the other side either follows automatically or fails to compile.
01 · The payoff

Define it once, get three things

An Effect Schema
validates every write, by person or agent

Drizzle tables
block_testimonials, plus its migration

Agent tools
add_testimonials and update_testimonials, with the exact fields, limits and descriptions

A content block, defined once. Each field knows its Effect Schema and its Drizzle column. The agent's tools are generated from the registry, so the model sees exactly what the database will accept: the descriptions are its documentation.
02

Why rigid frameworks are the best place for AI to work

Failures you can see guard against output you can't predict

Models are non-deterministic.
Compilers aren't.

So put the compiler between the model and production.

You can't make an LLM deterministic. You can make everything around it deterministic, so each wrong guess fails the same way, immediately, with a precise message.
02 · Mechanical failure

Two ways to be wrong

Silent failure

Loose stack

env.VECTOR is undefined at runtime

The model's JSON has "tags": "cat", and it gets saved anyway

A thrown error nobody knew about takes down a request

Found by users, in production, days later

Mechanical failure

Rigid stack

Type error at search.ts:42: no VECTOR on WebsiteEnv

Decode refused: tags must be an array. Sent back to the model.

The error is in the signature; unhandled, it doesn't compile

Found by the agent, in seconds, before anyone sees it

A mechanical failure is loud, immediate, located and explained. That's exactly the kind of feedback an agent is good at acting on. It reads the error, fixes the line, runs the check again.
02 · The gates

Every layer catches a different kind of wrong

Types Wrong binding names, missing fields, unhandled errors, missing services bun run check
Lint Conventions: design tokens only, the component kit only, no raw colors bun run lint
Tests Behavior, on in-memory SQLite built from the real migrations bun run test
Requests Bad input from people and models, refused with a list of fixes strict(schema)
Deploys A diff of what will be created, changed or deleted, before anything is alchemy plan
The first three are folded into one command, bun run verify, and the agent is told to run it until it's clean. The last two run whether or not anyone remembers.
02 · Example

The agent renames a binding

$ bun run check Error src/lib/server/search.ts:42:28 Property 'VECTORS' does not exist on type 'WebsiteEnv'. Did you mean 'VECTOR_INDEX'? Error src/lib/server/library.ts:17:31 Property 'VECTORS' does not exist on type 'WebsiteEnv'. Did you mean 'VECTOR_INDEX'? svelte-check found 2 errors

Illustrative output. With a JSON config, both lines would have deployed and returned undefined.

02 · Example

The model returns the wrong shape


{
  "alt": "Image of a cat on a windowsill",
  "name": "cat",
  "tags": "cat, kitten",
  "mood": "cozy"
}

What came back from the model

✗ decode refused (errors: 'all') ["tags"] Expected an array, got "cat, kitten" ["mood"] Unexpected key ["description"] Missing key → returned to the model as the tool result ✓ second try decodes; saved

Illustrative. Every issue at once, so one retry fixes all of them.

The schema goes out as JSON Schema, and what comes back is decoded, never trusted. With errors: 'all' the model gets the full list, not just the first problem. Errors are tagged classes whose messages are written for the agent to read.
02 · Example

It can't forget what might fail

Missing dependencies and unhandled errors are type errors, not 3 a.m. pages.

02 · Narrow the vocabulary

Fewer ways to do a thing, less variance

  • Infrastructure lives in one file
  • Writes are one shape: a remote function with a strict schema
  • Tables come from one source; migrations are generated, never hand-edited
  • UI uses one kit; lint refuses hand-built widgets and raw colors
  • Conventions in CLAUDE.md, enforced by lint, not by hope

"A color that isn't a token doesn't exist."

From the design-lint rules

Every convention an agent could get wrong either has a lint rule or a type behind it. Prose instructions are suggestions; a failing check is a fact.

03

How it's assembled

SvelteKit for the web, Cloudflare for everything else

Left to right: the browser only ever talks to one Worker, the SvelteKit app. Everything it reaches is a binding, and every binding is declared in alchemy.run.ts and typed into platform.env. The extra Workers exist because SvelteKit's generated Worker can't take queue messages, run on a cron, or export a Durable Object class. Outside Cloudflare: the model APIs for the agent, and Resend for email.
03 · The glue

Where the pieces meet

alchemy.run.ts Every resource and binding, the stages, the secrets. Exports WebsiteEnv. infra → types
app.d.ts App.Platform.env = WebsiteEnv: every route sees typed bindings types → app
*.schema.ts Drizzle tables → drizzle-kit generate → migrations/, applied by Alchemy on dev and deploy tables → SQL
*.input.ts Effect Schema for every write, wrapped in strict() for remote functions schema → forms
tools.ts Agent tools generated from the block registry, decoded strictly before they run schema → model
Layers Bindings become services once: workersAiEmbedder(env.AI), vectorizeIndex(env.VECTORS) bindings → services
workers/*.ts What SvelteKit's Worker can't do: queue consumers, crons, Durable Objects extra Workers

Zero to deployed

Setup for anyone who's never touched this stack

04 · Before you start

What you need

A Cloudflare account

Free. Add a domain to it later if you want a custom address.

A terminal

macOS, Linux, or Windows. The login steps need arrow keys, so a regular terminal, not an IDE panel.

A coding agent

Claude Code, or whichever you use. It does the typing; you make the decisions.

04 · Step 1

Install bun


# macOS / Linux
curl -fsSL https://bun.sh/install | bash

# Windows (PowerShell)
powershell -c "irm bun.sh/install.ps1 | iex"

# check it
bun --version

bun runs TypeScript directly and replaces npm for installs and scripts.

04 · Step 2

Install Wrangler, sign in to Cloudflare


# in your project
bun add -d wrangler@latest
bunx wrangler login

Cloudflare's CLI. Here it's for looking around: live logs, querying D1.


bunx wrangler tail <worker-name>
bunx wrangler d1 execute <db-name> --remote \
  --command "select count(*) from feedback"
							

# Alchemy keeps its own sign-in
bun alchemy profile edit --add Cloudflare

OAuth in the browser, saved to ~/.alchemy/profiles.json. Alchemy does the deploying, so no API tokens in env vars.

Wrangler isn't required for Alchemy to deploy: Alchemy signs in on its own. But Wrangler is still the quickest way to tail logs or run a query against the deployed database. The Alchemy command needs the project's dependencies installed, so it can come after the scaffold step.
04 · Step 3

Let the agent scaffold it

Help me build a SvelteKit app on Cloudflare with Alchemy v2, Effect 4, Drizzle on D1, and bun. Read https://alchemy.run/getting-started and https://alchemy.run/cloudflare/frontend/sveltekit and follow them exactly. For anything else, look it up in https://alchemy.run/llms.txt instead of guessing URLs or APIs.

Scaffold with bunx sv create (minimal, TypeScript, Drizzle with D1), add alchemy, @alchemy.run/cloudflare, effect, and write alchemy.run.ts with a D1 database bound to a Cloudflare.Website.SvelteKit. Type App.Platform.env with InferEnv.

Effect 4 is new: read node_modules/effect/AGENTS.md before writing Effect code. Add a verify script (types, lint, tests) and run it until it passes. Confirm with me before every deploy. Don't ask me to export API tokens.

Adapted from the prompt on alchemy.run's home page.

The two important parts: point it at the docs (Alchemy v2 and Effect 4 are newer than most models' training data), and give it a single command that tells it whether it's done.
04 · Step 4

Give it rails


{
  "scripts": {
    "dev": "alchemy dev",
    "check": "svelte-kit sync && svelte-check",
    "lint": "prettier --check . && eslint .",
    "verify": "bun run check && bun run lint && vitest --run",
    "db:generate": "drizzle-kit generate",
    "plan": "alchemy plan",
    "deploy": "alchemy deploy",
    "destroy": "alchemy destroy",
    "login": "alchemy profile edit --add Cloudflare"
  }
}

A CLAUDE.md at the root: the stack, the layout, the conventions, and the commands.

One done-check (bun run verify) the agent runs after every change.

Plain vite dev won't work because it has no platform.env. Always bun run dev.

04 · Step 5

Deploy


bun run dev                   # local D1, R2, email
bun run plan --stage demo     # what would change
bun run deploy --stage demo   # make it so
bun run destroy --stage demo  # take it all down
Plan: 3 to create + DB (Cloudflare.D1.Database) + Website (Cloudflare.Website.SvelteKit) + … Proceed? ◉ Yes ○ No ✓ DB created ✓ Website created { url: "https://….workers.dev" }

The first deploy asks to install Alchemy's state store in your account: say yes.

04 · Gotchas

Things that trip people up

  • Vectorize and Workers AI have no local emulation. Dev uses real ones in your account (free-tier sized).
  • Each stage reads its own .env.<stage>. Name every setting there, even empty ones, or it silently inherits dev's.
  • Resources are named after the stack. Rename the project and you get new, empty resources.
  • Migrations are generated, never hand-edited. Change the table, run db:generate, restart dev.
  • Run login and first deploy in a real terminal. The pickers need arrow keys.

05 · Prompt 1

Infrastructure

Using the setup prompt from before, create feedback-wall. In alchemy.run.ts, bind one D1 database (DB, migrations from ./migrations) and Workers AI (AI) to the SvelteKit Website, and export WebsiteEnv. No UI yet. Run verify.

What should come back

05 · Prompt 2

Schemas before code

Define FeedbackInput (text, trimmed, 1–280 characters, messages a person can act on) and Classification (sentiment: positive, neutral or negative; topic; summary) in Effect Schema, and a Drizzle feedback table to match. Generate the migration. Still no UI.

Schema first is the whole trick. Once these exist, every later step is constrained by them, and the agent's mistakes show up as type errors against them. Note the Classification has no length limits: structured output supports plain types and enums, so the descriptions do that job, and decoding checks the rest.
05 · The AI call

The schema goes out, the answer is decoded

Simplified. One Classification produces both the request's JSON Schema and the check on the reply.

05 · Prompt 3

The page, then the loop

Add the page: a form posting through a remote function with strict(FeedbackInput), which classifies the text and saves it, and the wall below it, grouped by sentiment, newest first. Then run bun run verify until it passes, and tell me each error you fixed.

"Tell me each error you fixed" is how the audience sees the gates working.

05 · Watch for

The failures we want to see

Types Wrong column or binding name, a Classification field the table doesn't have bun run check
Decode The model answers "mixed" for sentiment: refused, not saved Classification
Form An empty post, or 600 characters: the message appears on the field FeedbackInput
Deploy The plan lists exactly one database and one Worker, nothing else alchemy plan
If the agent gets everything right the first time, break something on purpose: rename the binding in alchemy.run.ts and run check, or post an empty form.
